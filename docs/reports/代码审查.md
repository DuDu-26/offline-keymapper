## P1：配置加载失败后，开始按钮可能启动旧布局

位置：`OverlayService.java:266-268`、`RootDaemon.java:100-109`、`MappingEngine.java:28-51`。

操作路径：先成功加载配置 A；切换到配置 B，B 使用界面允许但引擎不允许的值，例如视角灵敏度 20；点击开始。Overlay 连续发送 `config` 和 `start`。Daemon 对 config 会先 pause，但失败后 `configured` 仍是此前的 true；Engine 在校验阶段异常时仍保留 A。紧接的 start 启动 A，且清空 lastError。结果是界面和本地当前配置为 B，实际触摸仍使用 A，原先报错也被成功状态覆盖。

建议：每次处理 config 前先 `configured=false`，只有完整成功后才置 true。配置失败不得再启动。UI 等配置成功响应再发送 start；或让 start 指定配置 ID / 版本并与 daemon 当前加载身份比对。

## P2：编辑器和 ProfileStore 的可保存范围与引擎不一致

位置：`EditorDialogs.java:39-47,74-83`、`ProfileStore.java:37-39` 对照 `MappingEngine.java:45-46,60,156`。

| 字段 | UI / 存储允许 | 引擎实际行为 | 后果 |
|---|---|---|---|
| sensitivityX/Y | 0.05～30 | 大于10直接拒绝 | 设置成功但无法加载 |
| duration | 16～10000ms | 截成20～5000ms | 8秒滑动实际5秒，16ms实际20ms |
| interval | 30～10000ms | 截成30～5000ms | 8秒间隔实际5秒 |
| idleMs | 0～2000ms | 截成20～2000ms | 0或10ms无法按保存值执行 |
| Linux 114/115/116 | 通用checkCode允许 | Engine拒绝点位，daemon保留为系统键 | 输入保护键码能保存却无法启动 |

建议：共用配置约束常量，所有入口使用同一校验；不要默默改写用户保存的有效值。若范围需要收紧，同时改编辑器标签、校验及导入错误说明。系统保护键应在 UI、ProfileStore 与 Engine 三层一致保留。

## P2：导出读取“回调时当前配置”，可能导出错误内容并改变当前选择

位置：`MainActivity.java:73` 的导出分支和 `MainActivity.java:83` 的 request12。

导出 A 时先将 A 设成 current；文件选择器返回后再读取 `ProfileStore.current()`。文件选择期间悬浮球仍能打开并保存先前工作的配置 B，保存操作又会选择 B；最终名为 A 的文件包含 B。用户原本使用 B，仅查看并导出 A，也会无提示把 current 切到 A；daemon 未随此导出动作同步或暂停，界面与运行配置还可能分离。

建议：发起导出时保存 A 的不可变 JSON 快照，回调写该快照，不修改 selected。快照或对应请求状态要保存在 `savedInstanceState`，以支持文件选择期间 Activity 重建。导出前若编辑器有未保存内容，应明确以已保存版本或工作副本为来源，不能靠全局 current 间接选择。

## P2：Root 启动与停止的 generation 检查不覆盖握手提交及清理

位置：`RootBridge.java:66-75,83-84,93-99`。

stop 可以在 reader 等待握手期间增加 generation 并宣布停止；旧 launch 收到 ready 后，未再检查 ticket 就写 connected=true、activating=false 和已激活状态。旧 pump 的 finally 对 generation 的判断也在 synchronized cleanup 之外；停止、重启与旧连接退出交错时，可能在检查后清理被其他启动替换的共享 socket/child。

建议：在同一个 synchronized 块内验证 ticket 并提交握手状态；把连接和进程包装为带 ticket 的会话，cleanup 必须验证会话身份，只关闭自己拥有的对象。stop 应立刻关闭当前会话的 socket 解除阻塞，并终止当前子进程，不能只等待同一个 worker 队列。旧任务的 ready、error、finally 均不得修改新会话状态。

## P2：达到100个配置后，新建与添加游戏会抛到主线程并崩溃

位置：`ProfileStore.java:20`、`MainActivity.java:66,70,75`。

save 明确抛出“配置数量不能超过100”，但新建配置的 nameDialog positive 点击处理只校验名称，直接调用 action.accept，没有捕获；添加游戏的主线程选择回调也没有捕获 save 的异常。已有100条时点击新建保存或添加游戏，预期容量提示变成未捕获 RuntimeException。

建议：在这两个用户操作边界捕获并显示错误；nameDialog 保持打开或显示容量提示，不执行 render/dismiss。最好在创建入口提前提示已达上限，仍保留 save 的最终防线。

## P3：每次打开添加游戏都遗留一个单线程 executor

位置：`MainActivity.java:64`。

每次 `chooseGame()` 都创建新的 `Executors.newSingleThreadExecutor()`，任务结束后从未 shutdown。反复打开/取消游戏列表将持续累积闲置线程；Activity 退出也没有 executor 引用可清理。

建议：使用一个 Activity 持有的 executor 并在 onDestroy shutdown，或用单次 Thread；回调还应判断 isDestroyed，避免旧 Activity 返回时显示窗口。

## 检查边界

未见新增互联网访问缺陷：Manifest 没有 INTERNET；Java/C++ 实现仅使用本机 LocalSocket，没有 HTTP/TCP/DNS 客户端；文件选择器允许用户主动选择提供方，不应把云提供方的用户选择与 app 自己联网混淆。

未见未授权 Root 控制通道：RootDaemon 启动要求 UID0，抽象本地 socket 使用随机名称，接受命令前校验 peer UID 和随机 token。已存在 root 权限的其他进程不构成本次新增权限提升证据。控制协议只暴露配置、开始、暂停、状态和停止，不提供任意 shell 命令执行。

当前 duplicate code 校验是一个按键对应一个动作的产品限制，UI 已明确方向键不能与点位重复；没有充分依据将其认定为实现缺陷。若以后要支持同键多点，应作为明确功能变更处理。

库文件名错误已由主线修正为 `libmapper_input.so`，不计入当前未解决问题。触控性能、Root 管理器授权、SELinux、真键鼠和设备兼容性仍由主线的运行验收判断，本报告不以静态检查代替这些验证。
